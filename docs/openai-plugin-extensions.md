# OpenAI plugin extensions

Exeora exposes an MCP App at `ui://exeora/workspace` on both `/mcp` and `/p/:projectId/mcp`. Its React entry is `/dashboard/mcp-panel`, built alongside the dashboard and Chrome panel. All three reuse the same `Workspace` component. A separate global Sideapp at `ui://exeora/dashboard`, built as `/dashboard/mcp-dashboard`, reuses the full dashboard shell and routes.

## Behavior

1. ChatGPT can open **Exeora Workspace** from the conversation panel entrypoint. The model can invoke `exeora_open_panel` with optional `project`, `workspace`, `tab`, relative `path`, `diff` or `search` arguments. The resource requests the `fullscreen` display mode, which ChatGPT uses for entrypoints; the host ultimately decides the available placement.
2. `exeora_open_file` registers supported file extensions. It receives the host's `FileInput`, including an opaque `resourceUri`. When the host provides a filesystem path, Exeora resolves it against the connection's authorized project locations and workspaces. Otherwise the MCP App calls the app-only `exeora_resolve_file`, which receives `_meta["openai/resource"].path` from ChatGPT. A URI or basename alone is never treated as a filesystem path.
3. `exeora_settings_read` and `exeora_settings_update` provide native structured settings. The settings are a default project, default workspace, initial Files/Source Control/Search view, whether to show ignored files, and unified/split diffs. Every property has an effective default. Updates take `{ set: { ...changedProperties } }`, validate routing choices, and merge atomically in D1. Changing the default project clears its previous default workspace unless the update explicitly supplies a replacement.

4. **Exeora Dashboard** is a global entrypoint, opened from the host sidebar or by `exeora_open_dashboard({})`. It includes all existing dashboard routes and uses its own user sign-in.

Preferences are isolated by user, OAuth client, and endpoint. They persist in `plugin_settings` and are deleted with the account. Opening a particular workspace through a tool affects that panel instance; it does not change the connection's saved defaults or other conversations.

## Workspace navigation

`exeora_open_panel` preserves its tool name. The Workspace and Dashboard now use versioned `/v2` resource URIs so an older host-cached bundle is not mistaken for a relay-capable view; the original resource URIs remain readable aliases. `tab` accepts `explorer`, `search`, `source`, `pr`, `terminal` and `logs`. `path` opens an Explorer file. `diff: { path, area: "working" | "staged" }` opens Source Control, defaulting to `working`. `search: { query, regex?, caseSensitive?, wholeWord?, include?, exclude?, includeIgnored? }` applies the Search query and filters; omitted filters are false or empty strings. An empty query clears Search. Search strings are bounded to 1,000 characters. A content target infers its tab, and conflicting targets or an incompatible explicit tab are rejected.

The gateway exposes ordinary public server tools `exeora_workspace_get_state({ panelId })` and `exeora_workspace_navigate({ panelId, ...selection })`. `panelId` comes from the opening tool result or the `exeora/workspace` model context. It addresses one specific Workspace or signed-in Dashboard instance; there is no implicit most-recent-panel selection. These tools advertise no UI resource and never invoke `exeora_open_panel`. Refreshing the connection tools discovers them without requiring ChatGPT to discover app-instance tools. Native app tools remain available for compatible hosts, through the same controller.

Later navigation preserves omitted fields, including the current project/workspace and individual Search filters. Its actual UI result reports `applied`, `queued` if rendering has not settled within five seconds, `needs_confirmation`, `cancelled`, `error` or `superseded`. Changing tabs/files preserves buffers. Leaving dirty buffers waits for the person's confirmation. A private `exeora_panel_resolve_navigation` validates the fully resolved destination against the connection's current grants without rendering a widget. Metadata contains places, names and state; file contents enter context only through explicitly attached comments.

## Workspace command relay

A dedicated `WorkspacePanelRelay` Durable Object in the existing gateway owns each panel registration, independently of machine relays. The gateway binds the registration to the authenticated user, OAuth client and account/project endpoint. Public commands recheck that binding and current grants, including the returned state and pending destination. The UI obtains an app-only `exeora_panel_relay_ticket` from the MCP connection; tickets expire after 60 seconds, are one-use and are bound to a validated HTTPS ChatGPT sandbox origin. Registrations expire after 24 hours. Standalone Dashboard and Chrome views do not join the relay.

The socket must complete a protocol-1 readiness handshake. Each known command carries a request ID, explicit panel ID, connection generation and a 12-second absolute deadline. Acknowledgements must match both the request and its actual socket/generation; old connections cannot settle new requests. Timeout, caller cancellation, disconnect, Stop and session teardown cancel pending work without replaying navigation. A timeout reports an unknown outcome, never `applied`; read the state before retrying. Cancellation invalidates a still-waiting destination resolver so a late answer cannot move the UI. Cancellation after a route has already committed reports a queued outcome rather than claiming rollback. Incompatible protocol and replacement/expired-registration closes require reopening instead of reconnecting indefinitely.

The visible Agent control status offers Stop and Resume. Stop closes the relay and prevents native app-tool navigation too. Reconnects use fresh tickets and bounded backoff. The existing context writer adds panel ID and relay state beside navigation metadata while preserving attached comment groups; pending drafts remain private.

The Dashboard Sideapp connects only during its own signed-in session. It requests a pairing ticket through MCP, then exchanges it at `/api/panel-relay/ticket` using its separately authenticated Sideapp bearer. The server verifies the reserved Sideapp client, dashboard scope, trusted origin and the same user as the MCP owner. A different account cannot control that panel. Logout, token expiry and sign-in generation changes close the old connection and clear control metadata. Workspace navigation still uses the narrower MCP grant, even if the Dashboard's own account can see more projects.

## Selection comments and model context

The Workspace lets the user select text in an Explorer file or a line range in a Git diff and add a comment, both inside the ChatGPT plugin and in the standalone dashboard or Chrome panel. Each pending comment keeps the project, workspace, relative path, source kind, selected snippet and line range from that moment. File selections also record columns, the file version and whether there were unsaved edits. Diff comments identify the working or staged area, or the commit, and the old or new side. Moving to another file or view does not change an existing comment's source. The pending list supports review, editing and removal before sharing.

**Copy all comments** is available in every Workspace surface. It copies the selected snippets, comments and their provenance in the same format used for context attachments, without clearing the pending list. Inside the plugin it also includes Exeora comment groups currently attached to the conversation. Both plugin resources request `ui.permissions.clipboardWrite`; the host decides whether to grant it. A clipboard failure exposes selectable text for manual copying. A comment being edited must be saved or cancelled before copying or attaching the group.

**Add to context** appears only when the Workspace is mounted through the plugin integration, including the Dashboard Sideapp. It explicitly attaches the pending group to the current conversation through `ui/update-model-context`. A group is one titled text attachment containing the selected snippets, source locations and comments. Selections are not expanded to whole-file reads, and gateway/session credentials are never added. This action does not call `ui/message` or start an agent response. A failed or unsupported context update leaves the comments pending for retry. Plugin detection follows the injected host integration rather than the browser user agent or whether the page is framed.

Selections are bounded to 4,000 characters and 200 lines, comments to 4,000 characters, and a group to 25 comments and 40,000 formatted characters. Oversized input is refused with an explanation rather than silently truncated.

The protocol replaces an app instance's context on every update. Exeora composes navigation metadata with its attached groups so changing views does not erase them, and adding a later group preserves earlier attachments. Host context is authoritative when the panel mounts again or ChatGPT removes an attachment; a removed group must not be added back by a navigation update.

Pending comments never enter model context. The MCP Workspace panel keeps them per rendered conversation instance; when the host offers widget-state persistence, drafts use its private UI state rather than model-visible state. Without that optional facility they stay in memory while the panel remains mounted. The standalone dashboard and Chrome panel keep drafts in their signed-in UI tree. Dashboard Sideapp drafts are memory-only and are cleared on sign-out or token expiry, so another account cannot inherit private widget drafts. Attached groups are restored from `hostContext["openai/modelContext"]` when available. This is conversation attachment context for future turns, not an independently stored Exeora discussion or a guarantee of permanent chat-history storage. No database migration or CLI or Chrome extension release is required.

## Authorization and transport

The Workspace iframe receives no bearer or refresh token. Its API transport calls the app-only `exeora_panel_request` through MCP Apps, returning `{ status, body }` to the existing dashboard API client. Every request rechecks the current connection and project grant. The account endpoint returns only granted projects, machine entries, and terminal sessions. A project endpoint remains bound to its one project.

The proxy exposes only the Workspace routes for the picker, capabilities, reads, file/Git actions and live tickets. Account administration, credentials, provider configuration, AI generation, pull-request writes and workspace removal use the full dashboard. A project policy still restricts changes: readers respect the tool allowlist, file saves respect `write_file`, other mutations require unrestricted access, and actions requiring confirmation return a linkable dashboard instruction. Interactive terminals require an unrestricted policy. Both sockets use one-use tickets bound to a validated ChatGPT sandbox origin; socket ingress accepts that origin only with its corresponding ticket. Request cancellation reaches the relay.

Public JavaScript, CSS and fonts permit cross-origin fetching. The Dashboard Sideapp uses narrowly configured CORS for validated HTTPS ChatGPT sandbox origins and bearer requests; it does not share gateway cookies. Account API preflights reject other origins, and the response wrapper removes the OAuth provider's broader CORS headers before granting access to validated sandbox, dashboard or configured Chrome extension origins. Shared OAuth and MCP endpoints retain their provider CORS for browser MCP clients. Actual API requests still require the normal OAuth scopes and owner or admin checks. The UI resource declares only the gateway's resource, connection and base-URI origins, and rewrites build asset references to absolute URLs. The Chrome panel keeps its extension-only framing policy and authentication bridge.

## Dashboard Sideapp sign-in

The Sideapp discovers its reserved public client through `/oauth/sideapp-client`. It generates S256 PKCE locally, starts `/oauth/device/code`, shows the verification code and opens the first-party browser verification page through the host. The existing device flow expires after 600 seconds and polls initially every five seconds. After browser sign-in and consent, it redeems the one-use authorization code at `/oauth/token` with its verifier. Device grants reuse the existing D1 table; no new migration is required.

Only the reserved Sideapp UI client may use this flow with `dashboard:manage`. Third-party MCP clients retain their MCP-only scope ceiling. The Dashboard session belongs to the signed-in user and is stored only in the Sideapp session, with an in-memory fallback for blocked browser storage. The Workspace tools and transport do not receive this token or its broader permissions. Logout and token expiry end the Sideapp session. Live terminal/log tickets issued with a validated Sideapp bearer are bound to that sandbox origin.

## File routing limits

The OpenAI specification currently lists file entrypoints and filesystem access for **Desktop only**. Thread entrypoints and structured settings also support Work web and mobile. A file must belong to a project/workspace already exposed to this connection. A desktop file path does not identify a remote machine; equal paths on multiple machines require an explicit project/workspace selector. The most deeply nested matching checkout wins, and traversal, outside paths and ungranted projects are refused. The executor remains responsible for canonical filesystem and symlink confinement when the editor reads or writes the relative file.

Files without a registered suffix can still be opened from the Workspace explorer. Detached ChatGPT uploads do not automatically become Exeora workspace files.

The file entrypoint advertises `ui.visibility: ["model", "app"]` alongside its resource URI. ChatGPT's settings validator otherwise reports that the private `exeora_open_file` tool cannot render its widget. The transport and resolver remain app-only; file resolution still checks the connection's project grants and workspace confinement. Refresh the connection metadata after deployment to pick up this registration change.
